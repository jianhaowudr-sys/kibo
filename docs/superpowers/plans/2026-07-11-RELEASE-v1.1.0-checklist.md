# Kibo v1.1.0 發版檢查清單

分支 `release/v1.1.0`(領先 main）。以下標「👤 你做」的是只有你能過的關(我做不到:Supabase 存取、EAS 帳號、裝置)。

## 這版包含什麼(已實作 + tsc/verify 全綠)
- **D1 備份止血**:全 22 表備份、交易化匯入(失敗 rollback)、匯入前 safety-net 快照、resetDatabase 全刪。
- **E1 功能斷鏈**:today-meals 死卡遷移、通知權限 gate、喝水固定每日時間(修 iOS 64 上限)、AI 60s timeout、Android 返回守門。
- **E4 打磨**:period 中文化、版本字串動態、MiniMax 下架、SecureStore 金鑰、主題 hook 合併。
- **E2 部分**:warning token、KeyboardScreen、pet 頁主題化、diet/new 鍵盤避讓。
- **E3**:tab bar 吃主題(修 pixel 模式沒吃色票的 bug)、首頁空狀態卡 PixelCard、a11y label(月曆箭頭/modal 關閉鈕)、大字體防裁切。
- **D3**:schema drift 斷言(CI 守著,22 表 0 漂移)、種子交易化、FK orphan sweep。
- **D2 完整**:Supabase 005/006 + PROBE、本地 sync_uuid、sync_core、cloud_sync 接線、**pull 擴充到全 14 表**(重裝可完整還原)。
- **訓練體驗**:組列左滑刪除、點 ✓ 改「取消勾選」(退回計畫組保留數值)、**訓練 session 可恢復**(app 被回收後接續)。
- **深審修正**:warning token 加到死碼(modern 模式無效)、tab bar hairline 被 undefined 抹掉、PixelCard 對齊洩漏、FK sweep 順序、通知遷移/排程韌性、健康設定頁輸入框每打一字失焦、備份快照還原入口。

## ⚠️ 尚未完成(需聚焦後續,勿當已完成上架)

  - **005 仍然可以安全跑**:它的健康表 + profile 對齊好處與 uuid 路徑無關,跑了就修好 P1-5/6。
  - **006 目前絕對不可跑**(會讓 v1.1.0 自己的 push 也全掛,見該檔 header)。
  - ⚠️ **「開 ENABLE_UUID_SYNC」與「跑 006」是同一個決策點,不可分離**:cap=true 的 push 不送
    local_id,新雲端列 local_id 為 NULL;而 v1.0.7 的 pull 判斷 `localIds.has(null)` 恆為 false、
    SQLite 又自動配號 → **舊版 client 每次同步都重複插入、無上限**。兩者都必須等商店版本分佈
    顯示舊版占比 <10% 才動,且要先在測試 Supabase 專案演練 005 → app(cap=true) → 006 全流程。
- **E2 剩**:7 頁鍵盤接入(body/new、food-library/new、me、routine/new、exercise/new、feedback、onboarding)、hex 清理。
- **D3 FK 強制執行**:`ENABLE_FK_ENFORCEMENT = false`(src/db/client.ts)。orphan sweep 已做,但在已上架、FK 從未開過的 app 上打開會讓現有靜默成功的亂序寫入開始拋 SQLITE_CONSTRAINT,需完整裝置迴歸(建/刪課表、finishWorkout、備份匯入、雲端 pull)才可開。
- **像素風 Phase 2/3**:diet/routines/me 卡片、CTA 統一 PixelButton、PixelArt tab icon。
- **訓練中動作 chip 拖曳排序**:目前是長按跳 Alert(上移/下移/移除)。改拖曳需把 `flex-wrap` 版面改成橫向單列或直向清單(拖曳庫不支援 wrap),是版面取捨,待決。
- **批次③ 原生**:Apple Health/Widget 首次裝置 build 驗證(healthkit v14 adapter 名、workout activityType、Swift widget 編譯)。

## 發版前步驟(依序)

### 1. 👤 Supabase migration(決策:先測試專案演練)
1. Supabase SQL Editor 跑 `supabase/migrations/PROBE_online_schema.sql`,把結果貼回(核對線上真實 schema)。
2. 在**測試 Supabase 專案**跑 `005_sync_uuid_and_alignment.sql`,確認無誤(全冪等、純加法)。
3. 正式專案跑 005。**注意**:005 之後 v1.0.7 的健康資料 push 會立刻開始成功(免費止血),不影響舊版。
4. `006_drop_legacy_unique.sql` **先不要跑**——等 D2 接線完成 + v1.1.x 上架 + 舊版占比 <10% 後才跑(不可逆)。

### 1.5 👤 測試專案往返驗證(開 ENABLE_UUID_SYNC 前必做)
純函數測試**本質上抓不到**這類問題(三方 schema 對照、呼叫順序、例外傳播、PostgREST key 一致性)。
三輪深審共 6 P0 + 7 P1 裡,有一半是靠人工推演才發現的。唯一系統性的驗證是往返:
1. 測試專案跑 005 → app 開 `ENABLE_UUID_SYNC = true`(僅測試 build)
2. 本地造齊 14 張表的資料(含蛋/寵物含皮膚稀有度、掃過條碼的自訂食物、補記的喝水、分段睡眠)
3. fullSync → 清空本地(resetDatabase)→ fullSync
4. **逐欄 diff** 還原前後:欄位值、筆數、父子關係(workout→sets、routine→exercises、egg↔pet)
5. 再 fullSync 一次,確認**雲端沒有長出重複列**、本地筆數不變(這步抓 uuid 震盪)

### 4. 👤 裝置驗證(build 出來後)—— 依風險排序

**🔴 先驗這兩個,它們決定版面重構能不能上**
1. **Android + `edgeToEdgeEnabled: true` 的 diet/new 鍵盤**。edge-to-edge 下視窗不會像一般 `adjustResize` 那樣縮,底部 bar 可能**根本不會被鍵盤推上去**。第三方審查明確指出這是整個版面重構的成敗關鍵。
   → 記一餐,點最底部的熱量/蛋白輸入框,確認**輸入框與儲存鈕都看得到、能直接點**。
2. **iOS 的 diet/new 是 pageSheet modal** + `behavior='padding'` 可能雙重補償(內容被推太高)。同上操作。

**🟠 這輪新功能(我沒裝置,完全沒驗過)**
3. **組列左滑刪除**:訓練中左滑一組 → 出現「🗑 刪除這組」。**同時試著點該列的重量/次數輸入框改數字** —— 那列含 TextInput,水平手勢可能和輸入打架(Android 尤其)。
4. **點 ✓ 改成取消勾選**:已完成的組點 ✓ → 應退回計畫組並**保留重量/次數**,不是消失。
5. **訓練 session 可恢復**:訓練到一半(有已完成組 + 計畫組)→ 從系統殺掉 app → 重開 → 首頁應顯示「**繼續訓練**」→ 進去後已完成組、計畫組、動作佇列都還在。
6. **健康設定頁輸入框**:睡眠的目標上床/起床時間,**連續打字不應該每打一個字就失焦**(這是修好的既有 bug)。
7. **備份快照還原**:「我」頁 →「⏪ 還原匯入前的資料」→ 應列出時間點並能還原。

**🟡 既有修復的回歸驗證**
8. 備份:匯出→重裝→匯入,健康/自訂食物等 22 表列數一致;匯入舊 v3 檔;匯入壞檔資料無損。
