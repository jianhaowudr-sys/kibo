  - **005 仍然可以安全跑**:它的健康表 + profile 對齊好處與 uuid 路徑無關,跑了就修好 P1-5/6。

## 發版前步驟(依序)

### 1. 👤 Supabase migration(決策:先測試專案演練)
1. Supabase SQL Editor 跑 `supabase/migrations/PROBE_online_schema.sql`,把結果貼回(核對線上真實 schema)。
2. 在**測試 Supabase 專案**跑 `005_sync_uuid_and_alignment.sql`,確認無誤(全冪等、純加法)。
3. 正式專案跑 005。**注意**:005 之後 v1.0.7 的健康資料 push 會立刻開始成功(免費止血),不影響舊版。
4. `006_drop_legacy_unique.sql` **先不要跑**——等 D2 接線完成 + v1.1.x 上架 + 舊版占比 <10% 後才跑(不可逆)。

### 1.5 👤 測試專案往返驗證(開 ENABLE_UUID_SYNC 前必做)
純函數測試**本質上抓不到**這類問題(三方 schema 對照、呼叫順序、例外傳播、PostgREST key 一致性)。
三輪深審共 6 P0 + 7 P1 裡,有一半是靠人工推演才發現的。唯一系統性的驗證是往返:
1. 測試專案跑 005 → app 開 `ENABLE_UUID_SYNC = true`(僅測試 build)
2. 本地造齊 14 張表的資料(含蛋/寵物含皮膚稀有度、掃過條碼的自訂食物、補記的喝水、分段睡眠)
3. fullSync → 清空本地(resetDatabase)→ fullSync
4. **逐欄 diff** 還原前後:欄位值、筆數、父子關係(workout→sets、routine→exercises、egg↔pet)
5. 再 fullSync 一次,確認**雲端沒有長出重複列**、本地筆數不變(這步抓 uuid 震盪)
